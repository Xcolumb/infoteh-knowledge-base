# ADMIN_USERS_BUGFIX_REPORT — восстановление списка сотрудников

**Дата:** 19.11.2026.
**Ветка:** `feature/pto-modernization`.
**Инцидент:** у администратора не отображался список сотрудников; в браузере — `POST /api/auth/login → 401`, `GET /api/sotrudniki → 500`.
**Статус:** исправлено, проверено на реальной БД и в интерфейсе; данные и пароли сохранены.

---

## 1. Первопричина ошибки 401

Код авторизации не изменялся и работает штатно. В журнале приложения зафиксировано:

- `06:29:24` — `Неудачная попытка входа`, табельный номер `ADM001` (неверный пароль);
- `06:29:33` — успешный вход (`employeeId: 6`, роль «Администратор»);
- `06:31:16`, `06:37:18` — успешные входы `employeeId: 1` (ADM002).

То есть **401 был получен на неверный пароль** (или несуществующий табельный номер), а не из-за регрессии авторизации. После корректного ввода пароля вход выполняется, сессия создаётся, cookie и CSRF-токен выдаются. Повторная проверка подтвердила: верный пароль → `200`, неверный → `401`, заблокированный → `403`, слишком много попыток → `429`.

Ответ 401 намеренно не раскрывает, существует ли табельный номер (одинаковое сообщение и сравнение с фиктивным хешем).

## 2. Первопричина ошибки 500

Точное исключение из журнала:

```
SqliteError: no such column: "updated_at"
    at routes/staff.js:31
requestId: d76a94d5664c9621, b4693bb40e5a44b4, f2182b7a5d28739b
```

`GET /api/sotrudniki` выбирал поле `"updated_at" as updatedAt` из таблицы `"Сотрудник"`. Этого столбца в схеме нет и он **никогда не создавался миграциями**:

- миграция `001-base-schema` создаёт `Сотрудник` из 5 полей;
- `003-security-and-access` добавляет `Демо`, `Пароль_обновлён`, `Заблокирован`;
- `006-backfill-...` помечает демо-учётки;
- столбец `updated_at` добавлялся отдельным старым скриптом `migrate-updated-at.js` только для `Статья`, `Работа`, `Виды_работ`, но **не для `Сотрудник`**.

Проверка `PRAGMA table_info("Сотрудник")` на актуальной БД: `ID_сотрудника, Табельный_номер, Пароль, ФИО, Должность, Демо, Пароль_обновлён, Заблокирован`. Поля `updated_at` нет. Поэтому SQL падал на этапе `prepare`, до выполнения запроса.

Дополнительно: это поле не использовалось ни в интерфейсе (в таблице сотрудников нет колонки «Обновлён»), ни в других запросах. Единственное корректное и безопасное исправление — убрать обращение к несуществующему столбцу, не меняя схему и данные. Миграция не требуется: это не ошибка миграции, а расхождение кода со схемой.

Почему ошибку не поймали тесты: эндпоинт `GET /api/sotrudniki` не был покрыт автотестами (88 тестов проверяли другие сценарии). Добавлен отдельный набор.

## 4. Какие изменения выполнены

1. **Бэкенд.** Запрос списка приведён к фактической схеме: `id, tabNumber, fullName, role, demo, blocked, passwordUpdatedAt` + `objectIds`. Остальные административные операции не менялись.

4. **Тесты.** Добавлен регрессионный набор, который упал бы на старом коде (`GET /api/sotrudniki` → 500).

Безопасность не ослаблена: эндпоинт по-прежнему требует администратора (`assertAdmin`), аноним получает 401, инженер ПТО — 403; CSRF-защита, блокировка после неудачных попыток, аудит и сессии не менялись.

## 10. Известные ограничения

- Поле `updatedAt` больше не возвращается в списке сотрудников (его не было в БД и оно не отображалось в интерфейсе). При необходимости «даты обновления» потребуется отдельная миграция, заполнение и запись при изменениях — это осознанно не делалось, чтобы не менять схему в рамках исправления.
- 401 остаётся корректным ответом на неверный пароль; после 5 неудачных попыток действует блокировка на 15 минут (ответ 429).
- Независимый аудит безопасности и нагрузочные испытания по-прежнему не проводились.
- Проверка выполнена на локальной БД разработчика; на целевом сервере требуется повторить приёмку (вход, список, одна операция создания/блокировки).
