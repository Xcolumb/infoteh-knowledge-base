## 1. Краткое резюме проекта

**Что это.** Локальное веб-приложение (монолит на Node.js/Express + SQLite + «ванильный» фронтенд) с двумя функциональными контурами:

1. **Каталог знаний для монтажников:** «вид работ → работа → статья (инструкция)» с PDF-вложениями, поиском, фильтрами и ролями.
2. **Модуль ПТО (новый, не закоммичен):** реестр документов по объектам — исполнительная документация, ППР, акты скрытых работ, журналы работ, входной контроль; статусы, версии, история изменений, фильтры, выгрузка реестра в CSV.

**Ключевой вывод [В].** Продукт находится на уровне **функционального MVP с признаками рабочего прототипа**: предметная модель и пользовательские сценарии понятны и работают, но эксплуатационная зрелость (тесты, резервное копирование, аудит действий, безопасность файлов, документация API, развёртывание) отсутствует. Для пилота в одном подразделении (ПТО одного объекта) приложение пригодно после 1–2 недель доработок; для корпоративного внедрения — нет.

**Оценка готовности [О]** (по 10-балльной шкале, субъективно, критерии в §4):

| Критерий | Оценка | Комментарий |
| --- | --- | --- |
| Функциональная полнота для ПТО | 4/10 | Реестр и статусы есть; комплектности, замечаний, отчётности, объёмов нет |
| Техническая зрелость | 3/10 | Нет тестов, CI, миграций, мониторинга, документации API |
| Безопасность (предварительно) | 3/10 | Публичный доступ к файлам, нет аудита, нет rate limiting, HTTP без TLS |
| Эксплуатационная готовность | 2/10 | Нет бэкапов, нет процесса развёртывания, зависимость от версии Node |
| Масштабируемость | 3/10 | Один процесс, SQLite, отсутствие пагинации и внешнего хранилища |
| Потенциал автоматизации ПТО | 6/10 | Хорошая основа реестра и истории; не хватает связей документ↔акт↔объём |

**Сильные стороны [Ф/В]:**

- Понятная и компактная предметная модель (7 таблиц), без «переусложнения».
- Серверная проверка прав по роли из БД на каждом запросе (`requireAuth`/`requireRole`, `server.js:115–160`), а не только в интерфейсе.
- Пароли хранятся как bcrypt-хеши (`bcryptjs`, cost 10), а не в открытом виде.
- Модуль ПТО закрывает реальную потребность: статусы, сроки, ответственные, история изменений, реестр в CSV.
- Простой стек без сборки фронтенда: сопровождение посильно одному разработчику.
- Адаптивный интерфейс (проверено на 390×844), русскоязычный UI.

**Проблемы, мешающие внедрению [Ф/В]:**

- Файлы документов доступны **без авторизации** по прямой ссылке (`/uploads/...`) — см. §7.
- Нет резервного копирования, нет журнала действий пользователей (кроме истории ПТО и `console.log`).
- Нет смены пароля, политики паролей, блокировки после неудачных попыток.
- Единая файловая БД SQLite и один процесс — нет горизонтального масштабирования и отказоустойчивости.
- Часть функций реализована «в UI, но не в API» и наоборот (расхождения прав, см. §3.5).
- Отсутствуют тесты, CI, миграции как механизм, документация API.
- Незакоммиченный модуль ПТО: продукт не имеет стабильной версии.

### 2.2. Архитектурная схема (фактическая)

```
Пользователь
   │  (браузер, ПК/смартфон)
   ▼
Интерфейс: frontend-html/index.html + app.js + styles.css
   │  fetch('/api/...') с cookie infoteh.sid (HttpOnly, SameSite=Lax)
   │  файлы: <a href="/uploads/..."> — прямая раздача, без проверки сессии
   ▼
Сервер: Node.js + Express 5 (server.js, единый процесс, порт 3001)
   ├─ сессии: express-session MemoryStore (в оперативной памяти процесса)
   ├─ права: requireAuth → requireRole (роль читается из БД на каждый запрос)
   ├─ бизнес-логика: обработчики маршрутов (без отдельного слоя сервисов)
   ├─ загрузка файлов: multer → uploads/
   └─ статика: frontend-html/ и uploads/ (express.static)
   ▼
Хранилище: infoteh.db (SQLite, journal_mode=delete, foreign_keys=ON)
   + uploads/*.pdf|docx|xlsx (файловая система сервера)
   ▼
Внешние сервисы: отсутствуют
   (единственное внешнее обращение — Google Fonts из браузера пользователя)
```

### 2.4. Архитектурные особенности и технический долг [Ф/В]

1. **Отсутствие слоя сервисов.** Вся бизнес-логика — в обработчиках маршрутов `server.js`; повторяющиеся SELECT-конструкции (список/деталь статей, `server.js:585–643`) дублируются.
2. **Схема ПТО объявлена дважды:** в `server.js` (при старте) и в `migrate-pto.js`. Рассинхронизация при изменении полей вероятна.
3. **Справочники типов и статусов ПТО захардкожены дважды:** `PTO_TYPES`/`PTO_STATUSES` в `server.js:169–184` и в `frontend-html/app.js:124–150`. Изменение перечня статусов требует правки в двух местах.
4. **Порог входа в эксплуатацию:** порт `3001` в коде (`server.js:14`), нет `.env`/`.env.example`, нет Dockerfile, systemd-юнита, конфигурации reverse-proxy.
5. **Зависимость от ABI Node.js:** `better-sqlite3` — нативный модуль; при смене версии Node приложение падает с `NODE_MODULE_VERSION`. Фактически воспроизведено: на Node v26.13.0 модуль, собранный под Node 24 (ABI 137), не загрузился; потребовалась `npm rebuild better-sqlite3`. При этом `engines` допускает любую версию `>=20` — операционный риск, нужен фиксированный `.nvmrc`.
6. **Ошибки возвращаются клиенту текстом** `error.message` (33 вхождения в `server.js`) — утечка внутренних деталей (в т.ч. путей) при 500.
7. **Нет пагинации:** `/api/articles` и `/api/pto` возвращают все строки; `Статья.Текст_статьи` — полный текст в каждом ответе.
8. **Поиск каталога — на клиенте** по загруженному массиву (`app.js:521–535`); модуль ПТО использует серверный `LIKE '%...%'` (`server.js:751–780`) — оба решения не масштабируются на большой объём.
9. **Обработчик ошибок зарегистрирован до маршрута `DELETE /api/articles/:id`** (`server.js:1282`, маршрут `server.js:1295`), из-за чего ошибки этого маршрута идут в стандартный обработчик Express; маршрут ловит их сам, но паттерн хрупкий.
10. **Рендер интерфейса через `innerHTML`** — применено системно; экранирование есть (`escapeHtml`, `app.js:2017`), но любая новая вставка без него создаёт XSS-риск.

### 3.5. Расхождения между заявленным и фактическим поведением [Ф]

1. **Права на удаление статьи.** В интерфейсе кнопка «Удалить» отображается только администратору (`app.js:611`), но API `DELETE /api/articles/:id` разрешает и «Старшему монтажнику» (`server.js:1295`, `CONTENT_MANAGERS`). То есть ограничение обходится прямым запросом.
2. **`README.md`** описывает функции, которых нет: полнотекстовый поиск FTS5, PWA, CSRF, rate limiting, Redis-сессии — все перечислены в разделе «Планы по развитию», то есть корректно помечены как планы, но при беглом чтении могут восприниматься как реализованные.
3. **Пароли демо-учётных записей** приведены в `README.md` в открытом виде (значения здесь не раскрываются). Для пилота это допустимо, для эксплуатации — требует смены паролей и удаления таблицы из документации.

### 5.1. Что целесообразно разрабатывать в первую очередь [В]

1. **Комплектность ИД (№ 8) + связь с актами (№ 2, 3)** — это то, ради чего ПТО вообще нужен реестр; без этого продукт остаётся «папкой с файлами».
2. **Замечания и предписания (№ 5)** — процесс с жёсткими сроками и потерями при ручном учёте.
3. **Уведомления о сроках (§3.3, № 31)** — минимальная версия: ежедневная сводка просроченных документов (внутри системы или e-mail).
4. **Полнотекстовый поиск FTS5 (№ 4)** — относительно дешёвая доработка с высоким эффектом.
5. **Версии файлов (№ 11)** — снижает риск работы по устаревшей редакции.
6. **Письма/запросы (№ 6)** и **учёт объёмов (№ 10)** — только после уточнения требований заказчика (формы, интеграции с 1С).

### 5.2. Ограничения адаптации, которые нужно принять осознанно [В]

- Отсутствие объектной изоляции: любой авторизованный сотрудник видит документы всех объектов. Для пилота на одном объекте это допустимо, при мультиобъектном использовании — нет (§7, §8).
- Данные ПТО нельзя считать юридически значимыми: нет электронной подписи, нет неизменяемого журнала, нет юридически значимого согласования.
- Без интеграции с 1С/сметными системами объёмы и КС-2/КС-3 придётся вести вручную или полуавтоматически.

4. **Доверие.** ИИ-ответы без ссылок на источник нельзя использовать в работе ПТО; обязательна цитата (документ + страница/пункт).
5. **Никаких ИИ-функций в текущей версии нет** — в отчёте они разграничены: §6.1 — факт, §6.3 — предложения.

## 8. Оценка масштабируемости

### 8.1. Что подтверждено [Ф]

- Сервер — один процесс Node.js, слушает порт 3001 (`server.js:14`), без кластеризации и без внешнего балансировщика.
- Состояние сессий хранится в памяти процесса → перезапуск разлогинивает всех; несколько экземпляров приложения несовместимы без внешнего хранилища сессий.
- БД — один файл SQLite, `journal_mode=delete` (не WAL): одновременная запись сериализуется, читатели могут блокироваться на время записи.
- API не поддерживает пагинацию: `/api/articles` и `/api/pto` возвращают все строки (с полным текстом статей).
- Файлы — локальный диск сервера; общий доступ к ним из нескольких экземпляров приложения не предусмотрен.
- Ограничения по числу пользователей/файлов в коде отсутствуют; присутствуют только лимиты размера одного файла (10/20 МБ).

### 8.2. Оценка пределов (требует подтверждения нагрузочным тестом) [О]

| Параметр | Оценка | Обоснование |
| --- | --- | --- |
| Одновременные пользователи | 10–30 без деградации; выше — риск блокировок SQLite | Один процесс, синхронный драйвер `better-sqlite3` блокирует event loop на запросах; запись сериализуется |
| Объём документов в реестре | до ~10⁴–10⁵ записей | `LIKE '%...%'`-поиск и отсутствие пагинации становятся заметны раньше |
| Объём каталога статей | до ~10³ статей | Клиентская загрузка всех статей с текстом в браузер |
| Объём файлов | ограничен диском; нет квот | Файлы не дедуплицируются, версии не хранятся |
| Мультиобъектность | да, справочник объектов есть | Нет разграничения доступа по объектам |
| Мультиподразделения | нет | Нет рабочих пространств/тенантов |

### 8.3. Что потребуется при росте [В]

1. **Этап «малый пилот»:** ничего дополнительно, кроме бэкапов и HTTPS.
2. **Этап «несколько объектов / 30–100 пользователей»:** WAL-режим, пагинация, FTS5, внешнее хранилище сессий, вынос файлов в объектное хранилище (S3-совместимое, включая российские), reverse-proxy и мониторинг.
3. **Этап «подразделения / кластер»:** PostgreSQL вместо SQLite, несколько экземпляров приложения, очередь задач (уведомления, ИИ-обработка), SSO/LDAP, резервный узел БД.

### 8.4. Администрирование и поддержка [В]

- Сейчас: один администратор приложения (роль «Администратор»), техподдержка — разработчик; процедур и регламентов нет.
- Для эксплуатации понадобятся: регламент резервного копирования и восстановления, регламент обновления (с миграциями), журнал изменений, ответственный за контент (наполнение справочников), мониторинг доступности и диска.
- Ориентировочная нагрузка на сопровождение [О]: 0,1–0,2 FTE на поддержку одного объекта и 0,3–0,5 FTE на развитие (оценка, требует уточнения объёмом работ).

### 9.3. Методика расчёта эффекта и окупаемости

1. **Базовый замер (2–4 недели до пилота).** Для операций Э1–Э8 фиксируются: среднее время операции `t_before`, количество операций в месяц `N`, число пользователей.
2. **Замер после пилота (4–8 недель).** Те же метрики `t_after`, `N`, доля операций, выполненных в системе.
3. **Экономия времени:** `ΔT = (t_before − t_after) × N` (в часах за период).
4. **Денежная оценка:** `Э = ΔT × C_час`, где `C_час` — полная стоимость часа сотрудника с накладными.
5. **Совокупная стоимость владения:** `TCO = CapEx + Σ OpEx_t` за горизонт (например, 3 года).
6. **Чистый эффект и окупаемость:**
   - `NPV = Σ (Э_t − OpEx_t) / (1 + r)^t − CapEx`, где `r` — ставка дисконтирования организации;
   - срок окупаемости `PP = CapEx / (среднемесячная экономия − среднемесячный OpEx)`.
7. **Чувствительность:** пересчитать при `N` и `ΔT` в диапазоне ±30 %; отдельно показать сценарий «эффекта нет» (внедрение только как контроль и прозрачность).
8. **Нематериальные эффекты** (не входят в NPV, но важны для обоснования): снижение риска срыва сдачи ИД, единая точка знаний, снижение зависимости от конкретных сотрудников, готовность к проверкам.

### 9.4. Что нужно запросить у организации для расчёта

- численность ПТО и распределение ролей; количество объектов;
- среднемесячное количество документов по типам (ИД, ППР, акты, журналы, ВК);
- текущие трудозатраты на реестры/отчёты (хронометраж или экспертно);
- ставки/стоимость часа, ставка дисконтирования, горизонт планирования;
- требования заказчика к формам реестров и комплектности ИД;
- бюджет на ИТ и политика по внешним ИИ-сервисам.

## 10. Недостатки, ограничения и риски

### 10.1. Технические

1. Один процесс, один файл SQLite, отсутствие WAL и пагинации — ограничение нагрузки (см. §8).
2. Схема ПТО дублируется в `server.js` и `migrate-pto.js`; справочники типов/статусов продублированы на клиенте и сервере — риск рассинхронизации.
3. Нативный модуль `better-sqlite3` привязан к ABI Node: воспроизведён сбой при Node 26 после сборки под Node 24; версия Node не зафиксирована.
4. Нет слоя сервисов и валидации схемами: логика размазана по маршрутам, дублируются SELECT-конструкции.
5. Нет тестов, CI, линтера; регрессии выявляются только вручную.
6. Нет документации API (OpenAPI) и описания модели данных для новых разработчиков.
7. Ошибки отдаются клиенту текстом (`error.message`), в т.ч. пути файловой системы.
8. `uploads` раздаётся статикой без авторизации (R1).

### 10.2. Функциональные

1. Нет комплектности ИД, замечаний/предписаний, писем/запросов, учёта объёмов, отчётности — ключевых процессов ПТО.
2. Нет уведомлений о сроках (внутрисистемных и внешних).
3. Нет истории версий файлов и текста (только счётчик версии и метаданные).
4. Нет смены пароля, восстановления доступа, политики паролей.
5. Нет импорта/массовой загрузки и миграции действующих реестров.
6. Нет поиска по содержимому файлов и OCR.
7. Нет объектной изоляции и гранулярных прав.
8. Расхождение прав удаления статьи между UI и API.
9. Имена загружаемых файлов искажаются (кириллица → подчёркивания), оригинальное имя не сохраняется.

### 10.3. Эксплуатационные и организационные

1. Нет резервного копирования, мониторинга, логирования в файл, регламентов обновления.
2. Нет конфигурации развёртывания (Docker/systemd/nginx), порт и параметры зашиты в код.
3. Модуль ПТО не закоммичен; продукт не имеет стабильной версии и тега.
4. Демонстрационный контент и демо-учётные записи (пароли в `README`) непригодны для эксплуатации без замены.
5. Зависимость от одного разработчика: нет документации, тестов и передачи знаний.

### 10.4. Правовые и комплаенс

1. Персональные данные сотрудников (ФИО, табельные номера) обрабатываются без описанной политики и оснований (152-ФЗ требует оценки).
2. Документы ПТО могут содержать коммерческую тайну и проектную документацию с ограничениями правообладателя — нужен режим доступа и учёт.
3. Юридическая значимость: нет ЭЦП, нет неизменяемого журнала, нет согласования — документы в системе не заменяют подписанные оригиналы.
4. Передача документов внешним ИИ-провайдерам (при внедрении ИИ) требует правового решения.

## 12. Итоговые рекомендации для руководства

### 12.1. Рекомендуемый вариант внедрения

**Пилотный (поэтапный) на одном объекте — «Региональный ЦОД в г. Балаково»**, с горизонтом 8–12 недель и последующим решением о масштабировании.

Обоснование [В]:

- Продукт уже закрывает значимую часть контура ПТО (реестр, статусы, сроки, история, выгрузка), но не готов к корпоративной эксплуатации.
- Пилот ограниченного объёма дешевле и безопаснее: блокеры (R1, R2, R3) устраняются в первые 1–2 недели.
- Обратная связь реальных пользователей даст данные для бизнес-обоснования (метрики §9) вместо предположений.
- Полномасштабное внедрение сейчас привело бы к тиражированию незрелых процессов и повышенному риску утечки документов.

### 12.2. Критически необходимые доработки до пилота (блокеры)

1. Закрыть публичный доступ к файлам (`uploads`).
2. Настроить резервное копирование и проверить восстановление.
3. Ввести смену паролей/политику и убрать демо-учётки.
4. Обеспечить HTTPS и постоянный секрет сессии.
5. Зафиксировать версию кода и версию Node, документировать запуск.
6. Определить ответственного за контент и режим доступа к документам.

### 12.3. Функции с наибольшей практической пользой для ПТО (ранжировано) [В]

1. Реестр документов по объектам со статусами, сроками и историей (есть — развивать).

6. Отчёты/реестры по формам заказчика (частично).

### 12.4. Аргументы для обоснования перед руководством ООО «СтройМонтажГрупп» [В]

1. **Низкий порог входа:** используется существующая разработка; пилот требует доработок, а не создания системы «с нуля».
2. **Закрытие конкретных болей ПТО:** единый реестр вместо папок и мессенджеров, прозрачные статусы и сроки, история изменений, реестр для заказчика в Excel.
3. **Управляемость:** руководство видит, какие документы не готовы и что просрочено, — снижается риск срыва сдачи ИД.
4. **Сохранение знаний:** инструкции и решения не уходят вместе с сотрудником.
5. **Готовность к проверкам:** история и реестр упрощают подготовку к аудитам и проверкам заказчика.
6. **Поэтапное финансирование:** эффект можно измерять после каждого этапа, отказ от дальнейших вложений возможен на любой стадии.
7. **Отсутствие лицензионных платежей** (открытый стек) — стоимость владения ниже, чем у коммерческих СЭД/CDE [О, требует юридической проверки лицензий].

**Что нельзя обещать [В]:** замену юридически значимого документооборота (ЭЦП, согласования), интеграцию с 1С «из коробки», готовый ИИ-поиск по проектной документации без доработок, экономию без замеров.
