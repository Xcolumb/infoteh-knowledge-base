# SECURITY_REPORT — результаты устранения проблем и остаточные риски

**Дата:** 18.11.2026.
**Область:** веб-приложение «База знаний и реестр ПТО» (Node.js/Express/SQLite).
**Характер проверки:** архитектурный аудит кода и ручные проверки API/интерфейса. **Это не пентест и не заключение по информационной безопасности**; полноценный аудит и тестирование на проникновение не проводились.

## 2. Дополнительные меры

- **Загрузка файлов:** белый список расширений (PDF, DOC, DOCX, XLS, XLSX, TXT, MD, CSV), блокировка опасных MIME (`text/html`, исполняемые), лимит 20 МБ, один файл на запрос, случайные имена, удаление файла при ошибке записи.
- **SQL:** все запросы параметризованы; конкатенации пользовательских значений в SQL нет (проверено по коду).
- **XSS:** вывод экранируется (`escapeHtml`/`escapeAttr`), динамические `href` и `value` проходят экранирование.
- **Секреты:** в коде отсутствуют ключи и боевые пароли; демо-пароли вынесены в `SEED_*` переменные; `.env` в `.gitignore`.
- **Логи:** пароли, токены, cookie и содержимое документов в журнал не пишутся (маскирование полей).
- **Валидация:** централизованные проверки типов, дат, идентификаторов, статусов, справочников.
- **Устойчивость:** `busy_timeout`, WAL, внешние ключи, транзакции для импорта и смены прав.

| R1 | CSP разрешает inline-скрипты (`'unsafe-inline'`) | Средний | Интерфейс использует `onclick`-атрибуты. Для ужесточения нужно перевести обработчики на `addEventListener` и убрать `unsafe-inline` (отдельная задача) |

| R4 | Блокировка подбора пароля также в памяти | Низкий | При перезапуске сбрасывается; для строгих требований — хранение в БД |
| R5 | Нет двухфакторной аутентификации | Средний | Для внешнего доступа (подрядчики) — отдельная доработка |

| R7 | Отсутствие проверки подписи/юридической значимости документов | Высокий (для ИД) | Система не заменяет ЭЦП и бумажный оригинал; требуется отдельная интеграция |
| R8 | Персональные данные сотрудников (ФИО, табельный номер) | Средний | Нужна политика обработки ПДн, регламент доступа и хранения (152-ФЗ) |

## 5. Что должен сделать администратор VPS перед запуском

1. Установить HTTPS (Nginx + сертификат), включить `TRUST_PROXY=1`, `COOKIE_SECURE=1`.
2. Задать `SESSION_SECRET` (≥ 32 символов), `ALLOW_DEMO_ACCOUNTS=0`.
3. Закрыть каталоги `backups/` и `logs/` правами доступа; вынести их из веб-корня (они и так вне статики).
4. Заменить/отключить демо-учётные записи, установить реальные пароли.
5. Настроить ежедневный бэкап (`npm run backup`) и проверить восстановление на копии.
6. Ограничить доступ к серверу (SSH-ключи, файрвол), обновлять ОС и Node.js.
7. Настроить журналирование и контроль свободного места.
