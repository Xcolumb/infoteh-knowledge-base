# DATABASE_MIGRATIONS — миграции базы данных

**СУБД:** SQLite (файл `infoteh.db`, драйвер `better-sqlite3`).
**Механизм:** `lib/migrations/index.js` — упорядоченный список миграций, каждая выполняется один раз в транзакции и фиксируется в таблице `Миграции`.

---

## 1. Как это работает

```js
// lib/db.js
db.pragma('journal_mode = WAL');
db.pragma('synchronous = NORMAL');
db.pragma('foreign_keys = ON');
db.pragma('busy_timeout = 5000');
runMigrations(db);   // применяет недостающие миграции
```

Правила:

- миграции выполняются по порядку, пропуская уже применённые (по имени в `Миграции`);
- каждая миграция обёрнута в транзакцию: при ошибке изменения откатываются, запись в `Миграции` не создаётся;
- повторный запуск безопасен;
- схема больше не дублируется в `server.js`, `seed.js`, `migrate-pto.js` — единый источник здесь.

Ручной запуск: `npm run migrate` (скрипт `scripts/migrate.js`).

## 3. Структура после миграций

### Основной контур

| Таблица | Назначение |
| --- | --- |
| `Сотрудник` | учётные записи, роли, флаги `Демо` / `Заблокирован`, дата смены пароля |
| `Виды_работ` → `Работа` → `Статья` | каталог знаний |
| `Объект` | строительные объекты |
| `Документ_ПТО` | реестр документов (тип, шифр, раздел, статус, срок, ответственный, файл, версия, OCR-флаг) |
| `История_ПТО` | история изменений документа |
| `Редакция_ПТО` | редакции файлов (старые файлы сохраняются) |

### Доступ и безопасность

| Таблица | Назначение |
| --- | --- |
| `Доступ_объект` | какие объекты доступны сотруднику |
| `Сессия` | сессии (SQLite-хранилище) |
| `Аудит` | журнал действий пользователей |
| `Миграции` | реестр применённых миграций |

### ПТО-процессы

| Таблица | Назначение |
| --- | --- |
| `Комплект` | комплект ИД по объекту |
| `Требование_комплекта` | настраиваемый состав комплекта (не зашит в код) |
| `Документ_комплекта` | привязка документов к требованиям |
| `Замечание` | замечания/предписания |
| `Статус_замечания` | настраиваемый справочник статусов |
| `Комментарий_замечания`, `Вложение_замечания`, `История_замечания` | обсуждение, файлы, история |
| `Уведомление` | уведомления в приложении |

### Поиск

| Таблица | Назначение |
| --- | --- |
| `Поиск` (FTS5) | индекс: тип, id, объект, заголовок, дополнительные поля, текст |

## 4. Обновление существующей базы (переход с версии 1.0)

1. **Сделать копию:** `npm run backup` (или вручную скопировать `infoteh.db` и `uploads/`).
2. Остановить приложение.
3. Запустить `npm run migrate` (или просто `npm start` — миграции применятся при старте).
4. Проверить:
   - `Сотрудник` содержит новые поля, существующие записи сохранены;
   - `Документ_ПТО` содержит `Текст_извлечён`, `Требуется_OCR`, `Оригинальное_имя`;
   - у действующих сотрудников появились записи в `Доступ_объект` (по всем объектам — поведение не меняется);
   - у документов с файлами появились записи в `Редакция_ПТО`.
5. Запустить приложение, проверить вход, реестр и открытие файла.

Миграции не удаляют и не переименовывают существующие столбцы и таблицы.

---

## 5. Восстановление после неудачной миграции

Если миграция упала, изменения её транзакции откатились автоматически. Порядок действий:

```bash
sudo systemctl stop infoteh
node scripts/restore.js backups/backup-XXXX --force
sudo systemctl start infoteh
```

Скрипт восстановления сначала проверяет копию (`integrity_check` + контрольные суммы), затем делает страховочную копию текущего состояния и только после этого заменяет БД и файлы.

---

## 6. Резервное копирование и WAL

База работает в режиме WAL. Поэтому копирование «через копирование файла» при работающем приложении небезопасно.

- `scripts/backup.js` использует online backup API `better-sqlite3` — согласованный снимок без остановки сервера;
- копия проверяется `PRAGMA integrity_check` и контрольными суммами SHA-256;
- `uploads/` копируется рекурсивно;
- манифест `manifest.json` содержит размеры, хеши и количество записей по ключевым таблицам;
- ротация по `BACKUP_KEEP` (по умолчанию 14 копий).

---

## 7. Ограничения и рекомендации

- SQLite достаточно для пилота (3–5 пользователей, один объект). При переходе на несколько объектов и десятки одновременных пользователей рассмотреть PostgreSQL (отдельный этап, требуется миграция схемы).
- После восстановления копии на новом сервере индекс поиска перестраивается при первом запуске (проверьте `logs/app.log`: `Индекс поиска перестроен`).
- Не редактируйте `infoteh.db` вручную при работающем сервере.
- Резервные копии хранить вне сервера приложения.
